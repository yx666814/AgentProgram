# 产品需求

## 1. 产品概述

系统是一个本地桌面多 Agent 软件交付工作流。每个项目包含五个隔离聊天室，并由后端编排器控制阶段推进、产出校验、人工审批、返工和恢复。

## 2. 项目管理

### PR-PROJECT-001 创建项目

用户必须能够创建项目，并指定项目名称、目标描述和本地工作目录。

### PR-PROJECT-002 打开与恢复

用户必须能够重新打开已有项目。系统必须恢复聊天室、工作流、产出物、审批和事件状态。

### PR-PROJECT-003 工作目录边界

后端必须为每个项目保存规范化绝对路径。工具默认不能访问项目目录之外的内容。

### PR-PROJECT-004 项目状态

项目至少具有 `created`、`running`、`waiting_user`、`paused`、`failed`、`completed` 和 `stopped` 状态，与当前工作流的对外状态保持一致。

## 3. 五阶段工作流

### PR-WORKFLOW-001 固定阶段

MVP 必须提供 `planner`、`designer`、`builder`、`reviewer` 和 `deployer` 五个固定阶段。

### PR-WORKFLOW-002 顺序约束

后续阶段必须等待直接上游阶段完成质量门、必要审批和交接包生成。

### PR-WORKFLOW-003 控制操作

工作流必须支持 `start`、`pause`、`resume` 和 `stop`。暂停必须停止启动新任务，而不是只改变显示状态。

### PR-WORKFLOW-004 单实例运行

同一个项目不能同时运行两个工作流执行任务。

### PR-WORKFLOW-005 返工

质量门或 Reviewer 可以将工作退回 `Planner`、`Designer` 或 `Builder`。系统必须重置目标阶段及其下游阶段的失效结果。

### PR-WORKFLOW-006 返工上限

每个阶段必须具有可配置的最大返工次数。超过上限时工作流进入 `failed`，等待用户处理。

### PR-WORKFLOW-007 崩溃恢复

后端重启后必须能够恢复运行前状态。对于未完成的模型和工具任务，应标记为中断并由用户选择重试或终止。

## 4. 隔离聊天室

### PR-CHAT-001 一阶段一聊天室

每个项目必须具有五个聊天室，每个聊天室绑定一个阶段。

### PR-CHAT-002 独立上下文

聊天室必须独立保存消息、参与者、系统提示词、工具权限、任务和上下文预算。

### PR-CHAT-003 用户参与

用户必须能够在任意聊天室发送消息、提出修改意见并参与正式决策。

### PR-CHAT-004 多 Agent 参与

一个聊天室必须允许配置多个模型参与讨论。

### PR-CHAT-005 消息类型

消息至少区分：`user_message`、`agent_proposal`、`agent_consensus`、`system_event`、`tool_result`、`artifact_notice` 和 `approval_notice`。

### PR-CHAT-006 正式结论

普通聊天消息不能自动成为正式阶段结论。系统必须通过明确操作将讨论结果写入正式产出物或决策记录。

### PR-CHAT-007 历史保存

消息必须持久化并保持原始时间戳。重新连接时可以按顺序加载历史。

## 5. 多模型协作

### PR-MODEL-001 独立配置

每个阶段必须能够独立配置模型提供商、模型 ID、参数、启用状态和协调者身份。

### PR-MODEL-002 多方提案

多个参与模型可以并行生成提案，每个提案必须标明模型身份和状态。

### PR-MODEL-003 协调汇总

阶段可以指定一个协调模型，根据用户输入、参与提案和阶段上下文生成共识结果。

### PR-MODEL-004 局部失败

单个参与模型超时或失败时，不应自动取消已经成功或仍可继续的其他模型。

### PR-MODEL-005 取消与超时

用户必须能够取消模型任务。后端必须设置请求超时和最大重试次数。

### PR-MODEL-006 提供商

MVP 支持 OpenAI 兼容接口和 Anthropic 接口。模型适配层必须允许后续接入本地模型。

## 6. 阶段隔离与权限

### PR-PERMISSION-001 职责限制

每个阶段只能执行对应角色定义的操作。

### PR-PERMISSION-002 工具限制

后端必须按阶段提供工具，而不是向所有阶段暴露全部工具。

### PR-PERMISSION-003 文件限制

文件读取、写入、创建、删除和移动必须经过项目目录与阶段契约检查。

### PR-PERMISSION-004 Shell 一致性

Shell 命令不能绕过文件权限。命令的工作目录、可执行程序、参数和影响路径必须经过安全策略检查。

### PR-PERMISSION-005 高风险审批

删除、覆盖重要文件、提交 Git、安装依赖、访问网络和执行发布操作等高风险行为需要策略允许或用户批准。

### PR-PERMISSION-006 审计

每次工具调用必须记录发起角色、参数摘要、开始时间、结束时间、结果和影响文件。

### PR-PERMISSION-007 临时能力申请

角色需要使用默认能力之外的工具、命令或项目内路径时，必须创建结构化 `CapabilityRequest`。所有合法申请在 `MANUAL` 和 `AUTONOMOUS` 两种工作流模式下都必须弹窗由用户批准；批准只对声明任务有效。永久禁止能力不能通过申请获得。

## 7. 阶段产出与交接

### PR-ARTIFACT-001 正式产出物

每个阶段必须创建规定的正式产出物，并保存版本、创建者和生成时间。

### PR-ARTIFACT-002 阶段契约

阶段契约必须定义允许输入、必须输出、必需章节、文件权限和质量检查。

### PR-HANDOFF-001 标准交接包

阶段通过后，后端必须生成结构化 `HandoffPacket`。

### PR-HANDOFF-002 最小上下文传递

交接包只包含下游完成职责所需的信息，不包含上游完整聊天历史。

### PR-HANDOFF-003 不可变版本

被交接包引用的产出物版本必须保持可追踪。上游修改后必须重新运行质量门并产生新交接包。

## 8. 质量门与人工审批

### PR-GATE-001 自动检查

质量门应支持结构检查、必需章节检查、文件存在性检查、构建检查、测试检查和安全检查。

### PR-GATE-002 结果枚举

门禁结果使用 `PASS`、`WARNING`、`NEEDS_FIX` 和 `FAIL`。

### PR-GATE-003 阻断规则

`NEEDS_FIX` 和 `FAIL` 必须阻止交接。`WARNING` 是否放行由阶段策略或用户决定。

### PR-GATE-004 用户决策

用户可以作出 `approve`、`reject` 或 `request_changes` 决策，并可以附带反馈。

### PR-GATE-005 审批恢复

审批请求必须持久化。后端重启后，用户完成审批时工作流必须能够继续，而不是只修改节点显示状态。

## 9. Agent Runtime

### PR-RUNTIME-001 统一执行循环

后端必须统一处理提示词构造、模型调用、工具调用、工具结果反馈和最终输出。

### PR-RUNTIME-002 执行上限

每个任务必须具有最大模型轮数、最大工具调用数、最大运行时间和取消信号。

### PR-RUNTIME-003 重复检测

系统应检测重复工具调用和无进展循环，并安全停止任务。

### PR-RUNTIME-004 工具结果结构

工具结果必须使用统一结构，至少包含成功状态、数据、错误类型、错误信息和耗时。

### PR-RUNTIME-005 提示注入防护

来自项目文件、聊天消息和模型输出的内容不能扩大 Agent 权限。权限由后端策略决定。

## 10. 数据、事件和可观测性

### PR-DATA-001 持久化对象

必须持久化项目、工作流、节点、聊天室、消息、模型配置引用、任务、工具调用、产出物、交接包、门禁、审批和事件。

### PR-EVENT-001 实时事件

桌面端必须能够实时接收模型、工具、文件、节点、门禁、审批和错误事件。

### PR-EVENT-002 事件重放

客户端重新连接后可以从指定事件序号继续加载，避免重复加载全部历史。

### PR-OBS-001 运行记录

系统应记录模型耗时、Token 使用、工具耗时、阶段耗时、失败原因和单项目成本。

## 11. 桌面版安全要求

### PR-DESKTOP-001 本地监听

后端默认只监听 `127.0.0.1`。

### PR-DESKTOP-002 本地认证

桌面端启动后端时必须生成临时认证令牌。REST 和 WebSocket 都必须验证该令牌。

### PR-DESKTOP-003 密钥存储

API Key 不得保存在浏览器 `localStorage`，也不得通过普通读取接口原样返回。密钥应保存在操作系统安全存储中，数据库只保存密钥引用或脱敏信息。

### PR-DESKTOP-004 生命周期

桌面程序必须能够检测后端健康状态，并在安全条件下停止后端及其模型、工具子进程。

## 12. 非功能要求

- 状态操作必须具有明确的一致性边界。
- 同一项目的重要状态变更应串行化处理。
- 所有外部调用必须具有超时。
- 数据库结构应支持迁移。
- API 和事件协议应具有版本。
- 领域核心应能在不启动桌面界面的情况下测试。
- Windows 是第一版必须支持的平台。
