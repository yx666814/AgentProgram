# 规格文档计划

## 1. 目的

项目在后端实现前建立模块化规格库。每份文档只解决一个边界清楚的问题，避免产品需求、架构、接口和实施步骤混在一起。

## 2. 已建立文档

- `00-project-vision.md`：项目目的、原则和成功标准。
- `01-scope-and-roadmap.md`：MVP、非目标和开发路线。
- `02-product-requirements.md`：核心产品需求。
- `03-workflow-design.md`：五阶段状态与交接流程。
- `04-agent-roles.md`：五种 Agent 的职责和权限。
- `roles/README.md` 与 `roles/*-role-card.md`：五个阶段的详细角色卡、默认能力、权限申请、P2R 规则和系统提示词。

## 4. 推荐编写顺序

下一轮从 `06-stage-contracts.md` 开始，因为阶段契约决定数据模型、API、Agent 工具权限和质量门设计。

之后按以下顺序推进：

1. 阶段契约。
2. 交接协议。
3. 后端架构。
4. 数据模型。
5. API 与事件。
6. Agent Runtime。
7. 工具安全。
8. 状态恢复。
9. 桌面集成。
10. 测试策略。
11. 开发计划。

## 5. 单篇文档模板

每份规格至少包含：

1. 目的。
2. 范围。
3. 非目标。
4. 术语。
5. 核心规则。
6. 正常流程。
7. 异常流程。
8. 数据或接口定义。
9. 安全与权限。
10. 验收标准。
11. 已批准决策。

文档不得保留 `TBD`、`TODO` 或无法验证的“以后再说”。尚未讨论的主题不写入正式规则，而是留在本计划的后续文档列表中。

## 6. 架构决策记录

重要且难以逆转的决定应写入 `docs/decisions/`，使用架构决策记录（`ADR`）：

- 决策背景。
- 可选方案。
- 采用方案。
- 采用原因。
- 正面影响。
- 负面影响。
- 后续约束。

适合使用 ADR 的事项包括数据库选择、桌面框架、进程模型、密钥存储、工具沙箱和事件一致性策略。

## 7. 版本与变更规则

- 文档修改必须说明它影响的需求、协议或实现模块。
- 修改上游需求后，应检查所有下游文档是否失效。
- 已进入实现的协议字段不能静默改名。
- 不兼容协议变化必须增加版本或提供迁移方案。
- 历史文档不删除；过期文档应标记替代关系。
