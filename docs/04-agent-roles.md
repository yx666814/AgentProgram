# Agent 角色与职责

## 1. 通用规则

每个阶段是一个业务角色，而不是固定绑定某一个模型。一个角色聊天室可以包含多个参与模型、一个协调模型和用户。

所有角色必须遵守：

- 只处理本阶段职责。
- 只使用后端授予的工具。
- 只访问项目和阶段策略允许的文件。
- 不把普通讨论冒充正式产出物。
- 发现上游问题时创建返工请求，不私自改写已批准上游文档。
- 工具权限由后端强制执行，提示词不能扩大权限。

## 2. Planner

### 目标

把用户想法转化为明确、完整且可验收的项目需求。

### 输入

- 用户初始项目目标。
- 用户在 Planner 聊天室的补充说明。
- 项目约束和已有资料。

### 主要职责

- 澄清目标用户和使用场景。
- 定义功能需求和非功能需求。
- 划分 MVP 和后续范围。
- 定义验收标准。
- 识别依赖、风险和开放问题。
- 记录用户批准的正式决定。

### 正式产出

`specs/requirements.md`

必需内容：

- Project Goal
- Target Users
- Use Cases
- Functional Requirements
- Non-functional Requirements
- Constraints
- Out of Scope
- Acceptance Criteria
- Open Questions
- Decision Log

### 权限边界

- 可以读取项目背景资料。
- 可以写入 Planner 指定的需求产出路径。
- 不得写业务源代码。
- 不得执行安装、构建、提交或部署命令。

### 通过条件

- 没有阻断性的开放问题。
- 核心需求都有可执行验收标准。
- 范围和非目标明确。
- 用户批准正式需求。

## 3. Designer

### 目标

将批准需求转换为 Builder 可以直接执行的产品、技术和交互设计。

### 输入

- Planner 生成的 `HandoffPacket`。
- 已批准需求产出物。
- 用户在 Designer 聊天室的设计反馈。

### 主要职责

- 设计整体架构和模块边界。
- 设计数据模型、API 和事件协议。
- 设计 UI 页面、状态和交互流程。
- 确定技术栈和目录结构。
- 定义错误处理和安全边界。
- 把设计拆成明确构建任务。
- 建立需求到设计的追踪关系。

### 正式产出

- `specs/design.md`
- `specs/api.md`
- `specs/data-model.md`
- `specs/build-tasks.md`

### 权限边界

- 可以读取需求交接包和批准需求文件。
- 可以写入 Designer 指定的设计产出路径。
- 不得修改批准需求。
- 不得编写或修改业务代码。

### 通过条件

- 每个核心需求都有对应设计。
- 模块、接口、数据流和异常流程明确。
- Builder 不需要自行猜测关键架构决定。
- 重要设计决定得到用户批准。

## 4. Builder

### 目标

严格按照批准的需求和设计实现可以构建、测试和运行的项目。

### 输入

- Designer 生成的 `HandoffPacket`。
- 批准的需求和设计产出物。
- 当前返工反馈。

### 主要职责

- 编写生产代码。
- 编写单元测试和集成测试。
- 执行构建和测试。
- 维护实现文件清单。
- 报告设计偏差和未解决问题。
- 对需要改变需求或设计的问题提出返工请求。

### 正式产出

- 项目源代码。
- 项目测试。
- `specs/build-report.md`。

构建报告必须包含：

- Implemented Requirements
- Implemented Files
- Tests Added
- Build Commands
- Test Results
- Known Limitations
- Design Deviations
- Remaining Issues

### 权限边界

- 可以读取已批准需求和设计文件。
- 可以写入代码、测试、构建配置和 Builder 报告允许路径。
- 不得修改批准需求和设计文档。
- 安装依赖、Git 提交和高风险 Shell 操作需要策略许可或用户确认。

### 通过条件

- 声明实现的文件真实存在。
- 项目能够构建或启动。
- 规定测试通过。
- 不存在关键占位实现。
- 未经批准的设计偏差为零。

## 5. Reviewer

### 目标

独立验证实现是否满足需求、设计、质量和安全标准。

### 输入

- Builder 生成的 `HandoffPacket`。
- 已批准需求与设计。
- 代码、测试和构建报告。

### 主要职责

- 检查需求实现完整度。
- 检查设计一致性。
- 审查代码质量和异常处理。
- 执行构建、测试和安全检查。
- 检查占位实现、敏感信息和危险行为。
- 给出明确结论和返工目标。

### 正式产出

`specs/review.md`

结论只能是：

- `PASS`
- `NEEDS_FIX`
- `FAIL`

### 权限边界

- 默认只读需求、设计、代码和测试。
- 可以运行被批准的构建、测试和只读分析命令。
- 不得直接修改业务代码。
- 不得用“顺手修复”替代独立审查。

### 返工判断

- 需求错误或缺失：返回 Planner。
- 架构、接口、数据或交互问题：返回 Designer。
- 代码、测试和构建问题：返回 Builder。
- 严重安全或根本不可接受问题：`FAIL`。

### 通过条件

- 结论为 `PASS`。
- 所有阻断问题已经关闭。
- 必要构建和测试结果可验证。
- 用户完成规定审批。

## 6. Deployer

### 目标

把已批准实现整理为可验证、可安装和可交付的本地产物。

MVP 中的 Deployer 不直接操作真实生产环境。

### 输入

- Reviewer 生成的已批准 `HandoffPacket`。
- 通过审查的代码和测试。
- 项目构建与交付配置。

### 主要职责

- 执行最终构建。
- 执行 Smoke Test。
- 生成交付包和校验值。
- 生成版本、安装、启动和回滚说明。
- 汇总已知问题。
- 验证交付包在规定环境中可以运行。

### 正式产出

- `dist/` 或平台约定的交付目录。
- `specs/delivery.md`。

交付说明必须包含：

- Version
- Build Environment
- Build Command
- Test Summary
- Deliverables
- Checksums
- Installation
- Startup Instructions
- Known Issues
- Rollback Instructions

### 权限边界

- 可以读取已批准代码和交付配置。
- 可以写入交付目录和 Deployer 报告路径。
- 不得修改产品功能和业务逻辑。
- 发现代码或构建配置问题时返回 Builder。
- 不得未经用户明确授权访问线上生产环境。

### 通过条件

- Reviewer 结论为 `PASS`。
- 交付产物真实存在。
- 最终构建和 Smoke Test 通过。
- 安装、启动和回滚说明完整。

## 7. 用户角色

用户不是普通 Agent。用户具有以下能力：

- 参与所有聊天室。
- 配置和启停模型。
- 确认需求和重要设计决定。
- 批准、驳回或要求修改阶段结果。
- 批准高风险工具操作。
- 暂停、恢复和停止工作流。
- 查看完整审计记录。

用户操作同样必须记录时间、目标对象和决定内容。

## 8. 阶段内多 Agent 模式

每个聊天室可以包含：

- 多个参与模型（`Participant`）：分别提出方案、风险和改进意见。
- 一个协调模型（`Coordinator`）：综合参与提案和用户意见，生成共识草案。
- 用户（`Human Participant`）：提出要求并作出正式决定。

协调模型的输出仍然只是阶段草案。只有写入正式产出物并通过质量门后，才能作为交接内容。
