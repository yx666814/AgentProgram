# 项目范围与路线

## 1. 开发策略

项目采用“后端优先、协议先行、桌面集成随后”的开发顺序。

后端首先建立稳定的领域模型、状态机、聊天室、Agent Runtime、阶段契约、质量门、工具权限和持久化。桌面界面随后通过明确的 REST API、WebSocket 事件和本地进程协议接入。

## 2. MVP 范围

### 2.1 项目与工作流

- 单用户、本地运行。
- 可以创建和打开多个项目，但同一项目同一时刻只能有一个活动工作流实例。
- 固定五阶段工作流：`Planner → Designer → Builder → Reviewer → Deployer`。
- 支持启动、暂停、继续、停止、失败、返工和完成。
- 支持桌面应用与后端重启后的状态恢复。

### 2.2 聊天室

- 每个项目包含五个逻辑隔离的聊天室。
- 用户可以参与任意聊天室。
- 每个聊天室可以配置多个模型。
- 支持多模型分别提出意见，由协调模型形成阶段结论。
- 保存消息历史、正式结论、工具结果和系统事件。

### 2.3 Agent 与模型

- 支持 OpenAI 兼容接口。
- 支持 Anthropic 接口。
- 每个阶段可以独立配置模型、系统提示词、温度、超时和最大执行轮数。
- 单个参与模型失败时，其余模型仍可继续。
- 支持取消正在运行的模型任务。

### 2.4 阶段契约与交接

- 每个阶段具有固定输入、正式产出物、必须章节和通过条件。
- 只有通过质量门的阶段才能生成 `HandoffPacket`。
- 下游只接收正式交接包，不自动继承上游完整聊天记录。
- 交接包和产出物具有版本信息。

### 2.5 工具

- 文件读取、写入、目录浏览和搜索。
- Shell 命令执行。
- Git 状态、差异和提交。
- 构建、测试和日志读取。
- 项目目录沙箱、超时、输出限制和审计记录。
- 超出角色默认能力的高风险工具操作必须通过 CapabilityRequest 由用户确认；永久禁止操作直接拒绝。

### 2.6 数据与事件

- 使用 SQLite 保存项目状态和运行记录。
- 使用 WebSocket 向桌面端推送实时事件。
- 保存工作流事件，以便重连和重启后恢复界面。
- 保存产出物、审批、质量门结果和工具执行记录。

### 2.7 桌面集成基础

- 后端仅监听本机地址。
- 桌面程序可以启动、检测和关闭后端进程。
- 桌面端与后端之间使用临时认证令牌。
- 项目目录由用户通过桌面原生能力选择。
- API Key 使用操作系统安全存储或等价安全方案。

## 3. MVP 非目标

以下内容不属于第一版交付范围：

- 多用户、团队和组织权限。
- 云端托管和远程项目执行。
- 用户自由编辑任意 DAG 工作流。
- Agent 自动创建新角色或新 Agent。
- 插件市场和第三方工具市场。
- 多台机器并行执行。
- 自动操作真实生产环境。
- 自动发布到应用商店或云平台。
- 完全无人值守的高自主模式。
- 复杂计费、配额和商业账户体系。

## 4. 分阶段路线

### Phase 0：规格准备

- 固定项目目标和术语。
- 固定五阶段职责。
- 定义阶段契约和交接协议。
- 定义后端架构、数据模型、API 和事件协议。
- 定义安全、恢复和测试策略。

### Phase 1：后端领域核心

- 项目、聊天室、工作流和节点模型。
- 固定五阶段状态机。
- SQLite 持久化。
- 事件记录与恢复。
- 人工审批。

### Phase 2：Agent Runtime 与模型适配

- 统一模型接口。
- OpenAI 兼容和 Anthropic 适配。
- 阶段内多模型讨论。
- 协调模型汇总。
- 超时、取消和重试。

### Phase 3：工具与安全边界

- 文件、Shell、Git、构建和测试工具。
- 项目级沙箱。
- 阶段级工具和写入权限。
- CapabilityRequest 弹窗审批与永久禁止策略。
- 工具审计记录。

### Phase 4：质量门与交接

- 五类阶段契约。
- 结构、文件、构建、测试和审查门禁。
- `HandoffPacket` 生成和验证。
- 返工路由、重写历史和用户控制的继续/放弃机制。

### Phase 5：桌面端接入

- 本地后端进程管理。
- 项目与聊天室界面。
- 实时状态和审批界面。
- 模型与密钥配置。
- 崩溃恢复和应用退出处理。

### Phase 6：端到端验收

- 使用一个真实小型项目跑通五阶段。
- 验证暂停、重启、审批、返工和失败恢复。
- 验证 Agent 无法越权读取或修改文件。
- 验证最终交付物可以构建和运行。

## 5. 范围控制规则

- 新功能必须说明它服务于哪个 MVP 成功标准。
- 不影响五阶段闭环的扩展能力默认放入后续版本。
- 第一版优先保证状态正确、数据可恢复和权限可靠，不以模型数量和界面复杂度作为完成标准。
