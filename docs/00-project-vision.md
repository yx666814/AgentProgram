# 项目愿景

## 1. 项目名称

契约化多 Agent 软件交付编排平台。

## 2. 项目目的

本项目要构建一个桌面版软件开发协作系统。用户通过五个相互隔离的聊天室，与多个专职 Agent 共同完成一个软件项目从需求策划到最终交付的全过程。

系统的重点不是让多个模型自由聊天，而是建立一条可控制、可恢复、可审计的软件生产工作流：每个阶段只处理特定问题，只有产出物满足规定标准后，才能生成正式交接包并进入下一阶段。

## 3. 要解决的问题

通用编码 Agent 往往同时承担需求理解、架构设计、编码、测试和交付，容易出现以下问题：

- 单个上下文同时包含过多目标，注意力分散。
- 需求、设计和实现互相混杂，难以确定责任边界。
- 上游结论未经确认就被下游当成事实。
- 多个 Agent 共享全部历史，导致上下文膨胀和信息污染。
- 缺少可执行的阶段验收标准。
- Agent 可以越权修改不属于当前阶段的文件。
- 流程中断或桌面应用关闭后难以恢复。
- 用户难以知道某个决定由谁作出、何时作出以及影响了什么。

## 4. 核心方法

平台采用“固定五阶段、聊天室隔离、阶段内多 Agent、契约化交接、质量门禁、用户在回路”的方法。

五个阶段为：

1. 策划（`Planner`）
2. 设计（`Designer`）
3. 构建（`Builder`）
4. 审查（`Reviewer`）
5. 交付（`Deployer`）

编排器（`Orchestrator`）负责驱动状态、执行门禁和传递交接包。它不属于任何聊天室，也不作为第六个业务 Agent。

## 5. 核心原则

### 5.1 阶段专一

每个阶段只负责规定职责。职责边界必须同时由提示词、工具权限和文件权限保证，不能只依赖模型自觉。

### 5.2 上下文隔离

五个聊天室分别保存消息、模型、工具、任务和上下文。下游阶段不能直接读取上游聊天室的全部历史。

### 5.3 正式交接

阶段之间只传递经过批准的产出物、决策、验收标准、风险和允许使用的文件。非正式讨论不能自动成为下游输入。

### 5.4 标准先于传递

每个阶段必须满足阶段契约（`Stage Contract`）和质量门（`Quality Gate`）。没有通过门禁就不能启动下一阶段。

### 5.5 用户在回路

用户可以参与每个聊天室的讨论，并在关键节点批准、驳回或要求修改。第一版不追求完全自主运行。

### 5.6 可恢复

工作流状态、聊天消息、产出物版本、审批和事件必须持久化。应用重启后应恢复到可继续工作的状态。

### 5.7 最小权限

Agent 只能访问完成当前职责所需的模型、工具、目录和文件。Shell 命令必须服从与文件工具相同的边界。

### 5.8 可审计

模型调用、用户决定、工具执行、文件修改、质量检查和状态变化都应留下记录。

## 6. 目标用户

第一版面向单个本地用户，主要适合：

- 希望使用多个模型协作完成项目的个人开发者。
- 希望把需求、设计、编码和审查严格分开的项目负责人。
- 需要保留 Agent 决策、工具执行和项目产出记录的用户。

## 7. 第一版成功标准

第一版完成时，用户应当能够：

1. 在桌面应用中创建一个本地软件项目。
2. 在五个隔离聊天室中分别配置一个或多个模型。
3. 与当前阶段的多个 Agent 讨论并形成正式产出物。
4. 由后端自动检查产出物是否满足阶段标准。
5. 批准、驳回或要求修改阶段结果。
6. 通过标准化交接包把合格结果传递给下一阶段。
7. 在审查失败时将工作退回正确阶段。
8. 暂停、关闭并重新打开应用后继续工作流。
9. 查看模型调用、工具执行、文件修改和状态变化记录。
10. 最终得到可验证、可运行并带交付说明的项目产物。

## 8. 产品定位边界

第一版是本地桌面软件开发工作流，不是云端多租户平台，不是开放式 Agent 社交系统，也不是允许 Agent 任意创建角色和流程的通用自治框架。
